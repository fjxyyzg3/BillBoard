# BillBoard npm 依赖安全审查

用于 npm 公告、依赖升级、替换包或锁文件中的依赖解析变更。先确认目标仓库和授权范围，按受影响的安装入口审查。根项目和 `desktop` 各有独立 `package-lock.json`，发布或 CI 相关变更也要核对其实际使用的锁文件。

## 确认影响和修复依据

1. 对各相关安装入口执行 `npm audit --json --include=dev`。若需判断生产依赖，单独记录 `npm audit --omit=dev --json` 的结果。使用获准的 registry，审计会向其发送依赖信息。区分有效审计报告、网络或 registry 错误和未运行；按 GHSA 或 CVE 对照前后结果，记录其他未解决的公告。[npm audit 文档](https://docs.npmjs.com/cli/v11/commands/npm-audit/)
2. 对照上游公告的受影响版本、修复版本和触发条件。用锁文件、`npm explain` 和安装树定位每条受影响的依赖路径，包括间接依赖及别名。根据源码、配置和构建流程核实部署、开发、CI 或桌面打包实际使用的功能，记录可证实的范围。公告严重度和 BillBoard 的实际暴露分别报告。
3. 优先选择有上游修复的兼容版本或可移除受影响路径的上游更新，同步必要的配套包。若需采用第三方补丁，先静态审查精确发行版的包内容、源码提交、补丁差异、依赖和生命周期脚本。

## 以实际安装结果验收

1. 将新版本或 `overrides` 限定在所需依赖路径，核对各相关锁文件的实际版本、`resolved`、`integrity` 和无关变动。替换包使用可追溯的精确版本。公告因包名变化从审计结果消失时，还要确认旧的受影响副本已移除，且实际交付代码包含所需修复。
2. 使用第三方补丁时，可先在隔离环境以 `npm ci --ignore-scripts` 安装待审树。registry 支持时，用 `npm audit signatures` 核验候选包的签名和可用的来源证明。已有证明的校验失败须解决后再执行包代码；证明缺失时记录局限，并结合独立的包内容与源码证据判断。来源证明用于追溯包的构建和发布，修复效果来自独立的代码与行为证据。[npm 来源证明文档](https://docs.npmjs.com/generating-provenance-statements/)
3. 在干净环境用 `npm ci` 安装已审查的锁文件，复查实际依赖树并重跑同范围审计。选择能覆盖变更的构建、测试或打包检查，兼容性受平台影响时覆盖实际支持的平台。正式交付按 [AGENTS.md](../../../AGENTS.md) 执行全量验证，保留原始失败及补跑证据。
4. 报告各安装入口的目标公告是否清除、仍存在的公告和实际验证覆盖。若使用临时替换包，记录采用理由及回到官方版本的条件。获准推送后，核对远端 SHA 与相关锁文件是否对应已验证的版本。
