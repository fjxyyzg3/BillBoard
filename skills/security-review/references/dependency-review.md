# npm 依赖安全审查

适用于 npm 公告、依赖升级、替换包或锁文件中的解析变更。先确认实际安装入口和对应锁文件，覆盖变更涉及的部署、开发、CI 或打包流程。

## 确认影响

1. 在允许将依赖信息发送给所用 registry 时，按相关安装入口执行 `npm audit --json --include=dev`。需要单独判断生产依赖时，记录 `npm audit --omit=dev --json` 的结果。区分有效审计结果、网络或 registry 错误与未运行，按 GHSA 或 CVE 对照相关公告。[npm audit 文档](https://docs.npmjs.com/cli/v11/commands/npm-audit/)
2. 对照上游公告的受影响版本、修复版本和触发条件。结合锁文件、`npm explain` 和实际安装树定位依赖路径，包括间接依赖和别名。按源码、配置和构建流程判断相关功能是否进入受审产物或运行路径，分别报告公告严重度和项目实际暴露。

## 核验修复

1. 对获准的依赖修复优先采用上游兼容版本或移除受影响路径的更新，同步必要的配套包。将新增版本约束或 `overrides` 限于所需路径，替换包使用可追溯的精确版本。核对相关锁文件里的实际版本、`resolved`、`integrity` 及无关差异。包名变化使公告消失时，核验旧副本已移除且交付代码含有所需修复。
2. 使用第三方补丁时，静态核查精确发行版的包内容、源码提交、补丁差异、依赖和生命周期脚本。获准安装时，可先在隔离环境执行 `npm ci --ignore-scripts`。registry 支持时，用 `npm audit signatures` 核验签名及可用的来源证明。已有证明的校验失败须解决后才执行包代码；证明缺失时，记录局限并用独立的包内容与源码证据判断。修复效果以代码和行为证据为准。[npm 来源证明文档](https://docs.npmjs.com/generating-provenance-statements/)
3. 对已审查的锁文件，在可安全执行安装脚本的干净环境用 `npm ci` 安装，复查依赖树并重跑同范围审计。运行影响到的构建、测试或打包检查，覆盖受影响的支持平台，并满足项目的发布验收要求。
4. 报告各入口的目标公告处理结果、仍存在的公告和实际验证覆盖。临时替换包应记录采用理由及回到官方版本的条件。涉及获准推送时，核对远端 SHA 和锁文件是否对应已验证的版本。
