# 仓库公开与历史审查

适用于私有仓库原地公开、发布独立源码副本、核实曾进入 Git 或托管平台的敏感内容。日常公开推送先核对待推送差异及新增提交的作者、提交者邮箱。发现历史线索时扩大到对应引用和托管内容。

## 确认可见范围

1. 核对源库和目标库、可见性、受审提交与当前授权。存在多个远端且容易混淆时，使用只连接目标远端的干净审查副本。列出待公开远端的分支和标签（可用 `git ls-remote --branches --tags <remote>`），核对待公开树及这些引用可达的全部历史。检查提交作者和提交者邮箱、注释标签和提交说明。与登录身份重合的邮箱按隐私风险处理。
2. 用可脱敏输出的凭据扫描器覆盖受审历史，再按项目敏感信息类型补充定向检查，例如私有入口、附件链接、备份标识、业务数据及指向旧快照的 SHA 或链接。仅在本地比对已知私有值，报告类别和位置。记录扫描覆盖的引用、规则及局限。
3. 复核 PDF、表格和压缩包等测试样本的实际内容及元数据，包括 PDF 文本层、表格隐藏内容和包内文件。公开样本优先使用合成数据，使用真实数据时核对公开授权。用合成字段验证脱敏规则。对已人工复核的整份合成文件可保留完整性摘要。真实且可猜测字段的摘要和原始长度也要检查。
4. 使用获准身份检查实际存在的托管记录及制品，例如 Issue、PR、评论、Release 附件和 CI 日志。另行核对已知相关 fork、缓存视图和旧提交的可读状态。分别记录登录与匿名访问的结果，每项证据对应具体对象、入口和身份。[GitHub 敏感数据清理说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

对真实凭据，通过获准的管理渠道核实撤销或轮换状态。原地公开前按项目规则处理仍可读的敏感历史和托管内容。旧内容的托管状态缺少必需证据时，将公开验收标为待验证。

## 验收独立公开副本

需要保留源库私有时，可从已确认的源提交导出待公开快照，在独立仓库清理和审查。以无父提交的初始提交发布时，核对提交图及预期的公开作者、提交者身份。

1. 保持目标库私有，完成本地扫描及对应验证。若获准推送，从实际目标远端重新克隆，复核 SHA、文件范围、分支、标签、提交历史及适用的托管内容，并定向核对相关旧提交。用该远端的证据判定实际待公开内容。
2. 必需检查通过后，按授权调整目标库可见性，再用匿名访问验证目标库和预期源码可读。若源库应继续私有，同时复核源库的可见性和匿名访问状态。报告受审版本、访问身份、已确认风险和未验证范围。[GitHub 仓库可见性说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility)
