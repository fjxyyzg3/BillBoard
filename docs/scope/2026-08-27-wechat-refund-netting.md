# 微信支付退款净额导入

## 目标

微信支付官方 XLSX 会把原付款和退款分别列为支出与收入。现有解析器又会把状态中包含“退款”的两行都判为不可导入，用户无法直接得到扣除退款后的真实支出。本次改动让微信支付导入以原支出行的退款状态为金额依据：完全退款自动跳过，部分退款只导入原金额与退款金额的差额，并避免把退款收入再次计为收入。

## 决策基线

### 需求边界

- 处理微信支付官方 `.xlsx` 中的完全退款和部分退款；导入入口仍为 `/records/import`，不新增页面或来源。
- 部分退款的净额只从原支出行的 `金额(元)` 与 `当前状态` 中读取，不依赖退款收入行的订单号。附件证明退款收入与原支出的 `交易单号`、`商户单号` 不相等或为空，不能据此精确关联。
- 部分退款只生成一条净支出，沿用原支出的时间、交易类型、交易对方、分类映射、账单归属成员和创建人归属；退款收入不单独生成收入。
- 完全退款保留原支出金额用于预览核对，但以只读“已完全退款，自动跳过”结果进入草稿，用户不能改为保留，确认后不创建交易。
- 同一文件内的退款收入只在标准化后的 `交易对方` 非空且完全相同时汇总核对，不使用时间、商品、近似金额或订单号猜测逐笔配对。被同交易对方退款支出所声明的退款总额覆盖的收入自动忽略；超过覆盖金额的部分生成一条只读人工调整结果。空交易对方不得提供或消费覆盖额度。
- 若导出日期范围只包含退款收入而没有原支出，退款收入不作为收入导入，并明确提示用户手工调整原支出。
- 若原支出已经存在于当前家庭历史交易中，不自动修改、抵扣或软删除历史数据。当前净额与已导入净额一致时按普通同源重复处理；退款金额变化、变为完全退款或历史中仍是原金额时提示手工调整原支出。
- 历史判断包含软删除交易，并严格限制为当前 session 派生的 `householdId`；不得信任客户端传入的家庭或成员归属。
- 普通微信收入、支出、中性交易、关闭、失败及不能严格识别的退款状态保持现有行为；支付宝、随手记和招商银行导入不受影响。
- 金额继续使用整数分，日期继续按 `Asia/Shanghai` 解析。新增用户可见文案同步提供中文和英文。
- 附件只作为只读需求证据，不复制进仓库。测试只使用合成商户、订单号和金额，不写入附件中的真实交易标识。

### 严格识别规则

- 部分退款支出必须满足 `收/支=支出`，且 `当前状态` 完整匹配 `已退款(¥金额)`；实现可同时接受人民币符号 `¥` 和 `￥` 以及微信导出可能产生的等价全角括号，但不能接受状态中的任意数字或模糊包含关系。
- 状态中提取的退款金额必须大于零并严格小于原支出金额。等于或大于原金额却仍使用部分退款格式时，该支出标记为不可导入并显示明确原因。
- 完全退款支出必须满足 `收/支=支出` 且 `当前状态=已全额退款`；其退款覆盖金额按原支出金额计算。
- 退款收入分两阶段处理。候选识别只要求 `收/支=收入`、`交易类型` 以 `-退款` 结尾且 `当前状态` 完整匹配 `已退款¥金额`；候选随后单独校验状态金额与该行 `金额(元)` 是否相等。金额一致且交易对方非空时才是可参与汇总的严格退款收入；金额不一致时输出专用的“退款状态金额与流水金额不一致”无效原因；未命中候选格式的行才继续走现有单行校验。
- 标准化后的 `交易对方` 为空时，退款支出仍依据自身状态独立计算净额，但不提供汇总覆盖额度；退款收入候选无论金额是否一致都不能被自动覆盖，金额一致时进入人工调整结果，金额不一致时仍优先输出上述专用无效原因。
- 金额或日期无效的退款支出不可导入，也不能为同交易对方的退款收入提供覆盖额度。格式有效但没有对应退款支出覆盖的严格退款收入进入人工调整结果。
- 识别与汇总不依赖工作表行顺序；同一工作簿的多个工作表沿用现有表头查找与数据行上限。

### 技术决策

- 退款识别、净额计算和同文件退款收入汇总属于 `src/lib/imports/sources/wechat-pay.ts` 的来源解析职责，在生成通用 `ParsedImportRow` 之前完成；草稿层不重新解析微信原始状态。
- 解析器先收集标准化原始行，再按每条退款支出自身状态计算退款金额。`交易对方` 汇总只决定严格退款收入是否已被覆盖，不参与任何支出金额计算。
- 只对非空交易对方分别累计有效退款支出的覆盖金额和严格退款收入金额：收入合计不大于覆盖金额时消费这些退款收入；收入合计大于覆盖金额时，消费已覆盖部分，并为差额输出一条锁定的人工调整汇总结果。该结果的金额为未覆盖差额，显示信息来自该组最早的严格退款收入，但永不落库为交易。空交易对方的每笔有效退款收入候选均输出独立的锁定人工调整结果，避免互相消费额度。
- 部分退款结果的 `amountFen` 为原金额分减状态退款金额分。完全退款结果保留原金额分供预览，并携带非持久化退款处置类型。普通行继续复用现有单行解析。
- 微信退款支出的来源身份必须在退款金额后续变化时保持稳定，不能把可变的退款状态或净额作为身份的一部分。稳定指纹继续通过 `createSourceFingerprint` 生成，但固定使用以下载荷：`source=wechat_pay`、`transactionType=EXPENSE`、原支出 `交易时间`、原始 `金额(元)`、`交易类型`、`交易对方`、`商品`、`支付方式`、`交易单号`、`商户单号`、标准化备注，以及版本标记 `WECHAT_REFUND_ID_V1`；不包含退款状态、状态退款金额或计算后的净额。版本标记与订单号字段一起放入指纹输入的来源原始字段，避免与普通微信指纹命名空间混淆。普通微信行的现有指纹算法保持不变。
- 为兼容退款前已按旧指纹导入、随后可能被用户手工调整金额的微信支出，草稿创建除批量查询稳定退款身份指纹外，还使用已确认的保守旧历史回退：候选必须属于当前 session 家庭、`source=wechat_pay`、`transactionType=EXPENSE`，并与原支出具有完全相同的 `occurredAt`；部分退款候选的 `amountFen` 必须位于闭区间 `[当前净额, 原始金额]`，完全退款候选必须大于零且不超过原始金额。该回退不使用日期范围、近似时间或区间外金额。
- 旧历史回退恰好命中一条记录时，部分退款候选金额等于当前净额则按普通同源重复处理；金额高于当前净额且不超过原始金额，或当前为完全退款时提示人工调整。命中多条时无论金额组合如何均提示人工调整。未命中时不得继续猜测。用户已确认接受该保守回退可能把同秒、同来源且金额落入区间的无关交易锁定为人工核对；误判只会阻止自动导入，不会写入、修改或删除历史交易。
- 稳定指纹与旧历史回退查询均包含软删除记录，并按输入分块批量执行，禁止在交互式事务内逐行查询。草稿创建后的普通同源重复、退款金额变化和完全退款冲突继续按现有金额语义分类。
- 不新增 Prisma 模型、枚举、字段或迁移。`ParsedImportRow` 增加微信退款处理所需的类型和历史匹配信息；仅部分退款草稿把原始金额的整数分字符串写入现有 `ImportDraftRow.rawAmount`，供确认事务重新执行金额区间判断。该内部值不包含订单号、账号或商户标识，不进入页面摘要或最终 `Transaction`，草稿删除时随行删除；普通导入行和其它 `raw*` 字段继续保持现有最小化存储。
- 新增稳定原因代码 `WECHAT_FULLY_REFUNDED` 与 `WECHAT_REFUND_REQUIRES_MANUAL_ADJUSTMENT`。首次完全退款持久化为 `USER_SKIPPED/SKIP/WECHAT_FULLY_REFUNDED`；未覆盖退款收入持久化为 `USER_SKIPPED/SKIP/WECHAT_REFUND_REQUIRES_MANUAL_ADJUSTMENT`；已存在历史付款的冲突持久化为 `SOURCE_DUPLICATE/SKIP/WECHAT_REFUND_REQUIRES_MANUAL_ADJUSTMENT`。
- 页面把上述原因代码与现有支付宝退款结果共同归入“退款处理”区域。完全退款和人工调整结果均无保留控件，所有服务端行决策入口必须拒绝将其改为 `KEEP`；其它来源的普通 `USER_SKIPPED` 行保持可恢复行为。
- 确认导入不能只信任创建草稿时的历史分类。在确认事务内、任何 `Transaction` 写入前，服务端按当前家庭和来源再次分块批量查询所有待保留微信退款行的稳定指纹与保守旧历史回退候选，并复用同一分类函数。若任一行从可导入变为普通同源重复、完全退款冲突或人工调整，事务只更新相关草稿行的锁定状态，不写入本次任何交易，也不把草稿标记为完成；确认服务返回 `{ completedNow: false, requiresReview: true }`。用户复核后再次确认，才写入仍可导入的行。这样避免草稿创建与确认之间另一个导入写入原付款或不同净额。
- `confirmImportDraftAction` 必须消费 `requiresReview`：为 `true` 时不记录导入成功事件，不重定向到 `completed=1`，而是回到同一待处理草稿并携带稳定的 `IMPORT_DRAFT_CHANGED` 提示代码。导入页用新增中英文文案显示“草稿状态已变化，请复核”，并继续展示更新后的只读退款结果；只有 `completedNow=true` 时才进入现有完成路径。其它确认错误继续沿用现有错误处理。
- 汇总计数沿用现有类别：首次完全退款和未覆盖退款收入计入 `total`、`userSkipped`，不计入 `importable` 或 `invalid`；普通同源重复及历史退款冲突计入 `total`、`sourceDuplicate`。确认导入只写入仍可导入的净支出。

## 设计视图

### 功能设计

用户仍在 `/records/import` 选择微信支付并上传官方 XLSX。普通交易按原流程进入草稿。退款支出先读取自身状态：部分退款在预览中表现为一条金额已扣减的普通支出；完全退款显示在只读“退款处理”区域。账单成员选择和分类映射继续作用于可导入的净支出。

退款收入只作为核对信息，不再增加账本收入。解析器按同一交易对方汇总退款支出声明的覆盖金额与严格退款收入金额；全部被覆盖时不额外显示退款收入，存在未覆盖差额时显示一条“退款无法自动抵扣，请手工调整原支出”的只读结果。即使导出范围未包含退款收入，只要原支出状态包含有效退款金额，仍按该状态计算净额。

历史交易不被自动修改。首次导入净支出可正常进入分类映射、疑似重复和确认流程；重复导入相同净额按普通同源重复处理；退款继续增加、变为完全退款或命中退款前的历史原支出时显示人工调整提示。

### 技术设计

#### 解析流程

1. 加载工作簿、读取账单昵称、定位各工作表表头，收集全部原始数据行并保留工作表名和行号。
2. 严格分类部分退款支出、完全退款支出、严格退款收入和普通行；金额、日期或状态金额不合法的退款行进入不可导入结果。
3. 每条有效退款支出独立计算退款覆盖金额和净额；净额不依赖任何退款收入行。
4. 只按标准化后非空且完全相同的 `交易对方` 汇总有效退款覆盖金额与严格退款收入金额。消费已覆盖的收入；对未覆盖差额输出一条锁定人工调整结果；空交易对方不参与汇总。
5. 将普通行、部分退款净支出、完全退款结果和人工调整结果按原始位置稳定排序，生成 `ParsedImportWorkbook`；被消费的退款收入不再输出普通收入或无效行。
6. 草稿创建批量查询稳定来源指纹和保守旧历史回退候选，分类为首次净支出、普通同源重复、完全退款硬跳过或人工调整冲突；部分退款草稿同时在现有 `rawAmount` 保存原金额分，供确认复查使用。
7. 页面根据持久化状态和原因代码恢复只读展示；确认事务在写入前使用同一批量分类规则复查历史。发现状态变化时只锁定草稿行并返回 `requiresReview`，不写入任何交易；action 返回待复核草稿并显示提示。状态未变化时才写入可导入净支出并完成草稿。

#### 异常与保守处理

- 部分退款状态金额无法解析、为零、等于或超过原金额：原支出不可导入，显示金额异常原因。
- 退款收入候选的状态金额与行金额不一致：该行不可参与覆盖，输出专用无效原因，而不是回退为通用退款异常。
- 交易对方为空：退款支出仍独立计算净额但不提供覆盖额度；金额有效的退款收入候选进入人工调整，不能与其它空交易对方行聚合。
- 同交易对方退款收入总额超过有效退款支出覆盖金额：只读提示未覆盖差额，绝不将差额作为收入导入。
- 退款收入没有同文件退款支出：整笔退款金额作为未覆盖差额提示手工调整。
- 历史候选不唯一：保守提示人工调整，不导入第二笔净支出，不猜测具体历史记录。
- 未严格命中新增模式但状态仍包含退款、关闭或失败：继续沿用现有不可导入规则，不进行净额计算。

## 验收

- 同一账单含一笔 ¥2.00 支出，状态声明已退款 ¥1.19，并含一笔同交易对方 ¥1.19 严格退款收入 → 预览和最终账本只出现一笔 ¥0.81 支出；退款收入不出现为收入或额外人工调整结果；单元、集成和 E2E 测试断言。
- 部分退款支出存在但导出范围不含退款收入 → 仍按支出状态导入净额，不要求退款收入行存在；单元测试断言。
- 同一非空交易对方存在多笔退款支出或多笔退款收入 → 分别按支出状态计算每笔净额，再按双方汇总金额消费已覆盖收入；不按行顺序、时间或订单号猜测配对；单元测试断言。
- 严格退款收入总额大于同交易对方有效覆盖金额，或完全没有退款支出 → 未覆盖差额持久化为 `USER_SKIPPED/SKIP/WECHAT_REFUND_REQUIRES_MANUAL_ADJUSTMENT`，预览显示手工调整提示且不能改为保留，确认后不创建收入；集成测试断言。
- 完全退款支出且历史中没有原付款 → 持久化为 `USER_SKIPPED/SKIP/WECHAT_FULLY_REFUNDED`，预览保留原金额并显示“已完全退款，自动跳过”，无保留控件；服务端单行和批量决策均拒绝 `KEEP`，确认后不创建交易；集成及页面测试断言。
- 部分退款状态金额为零、等于或超过原金额，或退款收入候选的状态金额与行金额不一致 → 不参与净额或覆盖计算；金额不一致输出专用原因而非通用退款异常，其它有效行不受阻；单元测试断言。
- 交易对方为空的退款支出与退款收入 → 支出只按自身状态计算净额且不提供覆盖，金额有效的退款收入显示独立人工调整结果；不同空交易对方行不能互相消费额度；单元和集成测试断言。
- 原支出已按原金额存在于同家庭历史交易，且保守旧历史回退唯一或多笔命中，随后账单出现部分或完全退款 → 显示人工调整原支出，不自动修改历史记录且不新增净支出；同秒但金额在区间外的微信支出不得触发回退；集成测试覆盖唯一候选、多候选、区间边界与区间外金额、有效及软删除历史交易。
- 用户收到人工调整提示后把旧历史支出改成当前净额，再次导入相同账单 → 保守旧历史回退将其按普通重复处理；退款继续增加导致新净额降低，或变为完全退款 → 原历史金额落在新净额至原金额区间并显示人工调整，不新增交易；集成测试断言完整生命周期。
- 已通过稳定退款指纹正确导入当前净额后重复导入相同账单 → 按普通同源重复处理；随后退款金额增加或变为完全退款 → 改为人工调整提示，不新增交易；集成测试断言。
- 两个草稿交错创建，第二个草稿在第一个草稿预览后、确认前写入相同稳定指纹或保守旧历史付款 → 第一个草稿确认事务不写入任何交易，将变化行锁定并保持草稿待复核，返回 `requiresReview=true`；action 不记录成功事件、不跳转完成页，页面显示中英文复核提示及更新后的退款结果；用户再次确认后只处理仍可导入行。服务集成测试与 action/page 测试断言无重复交易、正确状态、重定向和提示。
- 历史匹配和同源查询不得跨家庭；另一家庭存在相同指纹、时间或金额不影响当前家庭导入；集成测试断言。
- 普通微信收入、普通支出、中性交易、关闭、失败、非严格退款状态，以及支付宝、随手记和招商银行导入结果保持不变；现有回归测试通过。
- 新增提示具备中英文文案，退款结果不要求分类映射或账单成员选择，且不会计入可导入数量；i18n、页面和集成测试断言。
- 只有微信部分退款草稿的 `rawAmount` 保存原金额分字符串；该值不出现在页面或最终交易，普通有效行、无效行及其它 `raw*` 字段仍保持现有最小化结果；集成与隐私测试断言。
