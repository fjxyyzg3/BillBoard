# 自然语言记账支持收入

## 目标

将现有自然语言支出输入扩展为收入与支出输入，让家庭成员在同一段文字中描述多笔收支，由 AI 自动识别交易类型、分类、日期及成员，校验后一次入账。

本 Spec 是本次扩展的实施基线，覆盖[原支出 Spec](2026-10-13-natural-language-accounting.md)中仅支持支出、拒绝收入／退款、仅发送支出分类及仅返回支出合计的约束；原 Spec 的入口、直接入账、家庭权限、时间参照、原子性、请求恢复和隐私机制继续有效。原文档保留为历史批准记录。

## 决策基线

### 需求边界

- 在 `/add` 的现有自然语言模式增加收入支持。保持一个多行文本框和一个“导入”按钮，不增加收支类型选择器、预览或二次确认；默认进入手工填写，两模式保留当前页面草稿及已有冻结行为。
- 一次输入可包含单笔、多笔收入、支出或混合收支；上限仍为 2,000 个字符、合计 20 笔交易。AI 必须逐笔明确判定 `INCOME` 或 `EXPENSE`，不能把含糊类型默认当支出、跳过片段或部分入账。
- 收入使用现有启用的收入分类，包含工资、奖金、报销、退款、投资及其他明确收入；支出使用现有启用的支出分类。不创建分类或成员，名称相同但类型不同的分类不能混用。
- 退款作为一笔正金额收入记录，与现有手工收入记账一致；不查找、修改、抵扣或冲销原支出，也不自动关联旧记录。报销同样作为收入新增。金额只按本次明确描述记录，不推算或补录历史金额。
- 纯资金转移，例如本人账户互转或家庭成员之间转账，仍不作为收入／支出。明确表达工资、退款等收入的到账可以记录，付款渠道或“转账到账”的措辞不能单独作为拒绝依据。外币、记录修改／删除及无法确定收支性质的片段仍整段拒绝。
- 收入归实际获得该收入的家庭成员；外部付款单位、资金提供人不是收入归属。例如“老婆收到单位奖金 500 元”归另一位家庭成员，“我收到退款 100 元”归提交者。未明确收入获得者时默认当前登录成员；成员含糊或无法映射当前家庭时要求修改。支出沿用实际付款成员规则，创建人始终为提交者。
- 日期、时间和缺省成员沿用原规则：首次受理的上海时间作为固定参照，未给日期／时间使用该参照，只给日期为 `00:00`，相对日期重试不漂移。金额必须有明确依据，不能猜测、凑整或用负数表达收入／支出方向。
- 所有交易及其分类、日期和成员均通过校验后一起入账；任一笔缺失、含糊、不支持或无效，整段不写入，保留当前页面原文并提示问题片段。成功清空输入，显示总笔数，按本批实际包含的类型分别显示收入／支出合计，不把两类金额混成净额或一个未标明类型的合计。
- 中英文标签、示例、错误和成功提示同步支持收支。收入和混合记录在现有记录页、家庭汇总、时间范围、编辑／删除入口中按现有交易类型行为展示。手工填写和文件导入维持各自现有行为。
- 新收入记录仍属于 AI 辅助手工输入，`source`、`sourceFingerprint`、`sourceImportedAt` 为空。尤其不能把这里的退款规则应用到文件账单原有的退款抵扣／去重流程。

### 技术决策

- 复用现有独立 `import-agent` 容器、自然语言内部端点、受限 Codex ACP 运行器与模型配置，不引入供应商设置、公开端点、工具权限或额外账本上下文。分类建议协议保持独立。
- 自然语言协议升级为 `natural-language-entry.v2`。请求候选包含现有启用收支分类的匿名 ID、名称和类型，成员仍使用匿名 ID 及当前家庭显示名称；返回统一交易数组，每笔显式携带收支类型及原有金额、日期、成员、分类、备注和有界原文依据。错误仍采用固定问题类型及偏移，不返回部分交易。
- 应用独立严格校验交易类型，确认所选分类的类型与该交易完全相同；在提交事务内批量重验分类仍启用、类型和名称未变，成员仍属于当前家庭。输入、候选名称和模型输出均不可信，合法 JSON 不能替代这些检查。
- 交易金额依然保存正整数分 `amountFen`，单笔上限遵循现有数据库整数限制。类型决定收入／支出，模型和持久层不使用带符号金额来暗示方向。两个方向的笔数与整数分合计从将要写入的已校验记录计算，并与整批记录在同一短事务中保存。
- 现有 `Transaction` 已支持 `INCOME`／`EXPENSE`，提交模型的 `result` 已是 JSON；本次不新增表、列或历史交易回填。成功快照需保存总笔数、两类各自笔数／金额及交易 ID；总笔数等于两类笔数之和，也等于 ID 数量，一类零笔时合计为零，有记录时合计必须为正且在相应笔数允许的范围内。
- 结果版本兼容在服务端读取快照时处理：已有仅含总笔数／总金额／交易 ID 的成功结果来自旧纯支出功能，按全部支出返回等值摘要，不改写旧行，也不查询现有交易重新计算。新增摘要结构使用可明确识别的版本，错误与问题偏移兼容原白名单及有界约束；不合法快照不能伪造成功。
- 请求身份仍为 session 派生的家庭、提交成员和客户端 UUID，不把交易类型或协议版本加入去重身份。成功、明确失败和未受理关闭标记均保持原终态；旧版本曾拒绝的收入／退款不能以原 UUID 重开，用户要主动发起新请求。旧交易后来编辑、删除或改变类型，不能改变原提交快照或触发重建。
- 沿用现有有时限尝试、固定时间参照和数据库互斥，涵盖尚无记录时的首次受理／查询关闭竞争及恢复后的迟到尝试。收入和混合批次共用同一次全批写入，不分两次事务或分两次调用模型；调用前和 AI 返回后都确认有效、未过期且未撤销的 AppSession。
- web 与 Agent 按一个发布单元更新；协议版本或字段不匹配时拒绝整批，不通过猜测缺失类型兼容模型响应。升级前已打开的页面可刷新后获得新文案和协议，并用原成员作用域 UUID 查询已有结果；旧脚本不能将无法展示的混合结果误报为旧版支出合计，必要时要求刷新并保留待确认 UUID，不宣告确定未入账。不承诺旧页面无需刷新即可使用新收入能力。
- 持续只发送本次文本、固定时间参照、必要收支分类与当前家庭成员候选，不发送历史账本、真实数据库 ID、账号或凭据。原文和模型输出仅在当前处理／页面内存中保留；浏览器仍只暂存待确认 UUID，刷新后不恢复原文。
- 首次成功后按本批实际包含的交易类型写最小活动记录，混合批次可按收入／支出各一条，metadata 只包含类型与该类型笔数。不把金额、原文、备注或成员名称放入活动、诊断、URL、日志或分析；重放不再次产生创建活动，活动或缓存失败不改写已提交成功。

## 设计视图

### 功能设计

用户在自然语言模式输入“工资到账 8000 元，午饭花了 35 元”，点击导入。页面冻结原文快照并显示处理中，完成后显示“已记 2 笔，收入 ¥8,000.00，支出 ¥35.00”，清空输入，保持可连续记账。纯收入或纯支出仅展示对应方向的合计，不要求显示无记录方向的零金额。

输入“老婆收到单位奖金 500 元，我收到退款 100 元”时新增两笔收入，分别归另一位成员和提交者；原支出保持原值。输入“工资到账 8000 元，午饭忘了多少钱”或仅说明成员间资金转移时，整段无新增记录，提示当前页面原文中的问题片段。

提交中、未知结果及恢复交互沿用当前页面状态机。成功响应丢失后确认原 UUID，返回已保存的收支摘要，不再次解析或创建记录。旧纯支出成功结果也能直接重放；旧收入不支持导致的终态失败保持失败，新功能通过新 UUID 使用。

### 技术设计

#### 整体方案

现有组件收集文本和 UUID，受保护 Action 受理后构造 v2 分类／成员候选及固定上海时间；ACP 在隔离运行器中识别全部交易。应用验证结构和候选关系，重新确认 session，然后由已有提交服务一次写入带类型的交易与版本化成功摘要。结果格式化由中英文文案负责，状态持久化和原文保留仍各自归服务端及当前页面。

交易类型与分类类型在协议校验和提交前重验两处建立对应关系。新结果只由同事务中的记录计算，查询仅重放存储的结果；兼容分支识别旧快照后形成等值纯支出展示，不依赖可变的交易表。提交表唯一键、占用和锁保持原机制，类型扩展不引入第二条写账通道。

#### 关键结构

- v2 分类候选增加 `INCOME`／`EXPENSE` 类型，别名仍唯一；即使两种分类都叫 `Other`，模型和应用也能按 ID 与类型分别选择。
- v2 成功响应统一使用 `transactions`，每项包含显式 `type`、`amountFen`、`occurredAt`、`memberId`、`categoryId`、`note`、`start`、`end`。缺少、未知或额外字段，以及类型与分类不匹配，均不能进入写入阶段。
- 新成功快照版本与类型汇总可严格区分旧快照；给页面的结果仅包含请求标识、状态及类型汇总，不增加交易明细、ID 列表或持久原文。旧错误码／问题类型继续能安全映射本地化提示。

#### 实现流程

1. 页面规范化本次文本并创建 UUID；服务端检查 session，按原身份键互斥受理。已有终态直接重放，已有处理状态按原占用规则返回或恢复。
2. 加载启用收支分类和当前家庭成员，形成含分类类型的匿名候选，使用首次受理时间调用 v2 自然语言协议。相同名称的不同类型保持独立候选。
3. 模型返回纠错、协议异常或不支持片段时，通过原有效尝试写入固定终态失败；原文由页面保留。正常结果通过整数分、日期、原文依据、显式类型和候选关系校验，再确认 session。
4. 持有当前有效尝试时进入短事务，批量重验分类和成员，一次创建收入／支出记录，保存版本化两类汇总及成功状态。事务失败时全批回滚，旧尝试或已关闭请求不能写入。
5. 事务后按类型记录最小活动并更新缓存；页面按本批实际类型显示摘要并清空文本。重试、查询、刷新恢复统一从不可变提交快照返回，旧快照通过兼容分支展示。

## 验收

- 单笔／多笔工资、奖金、报销、退款、投资及其他明确收入 → 按现有启用收入分类新增正整数分 `INCOME` 记录，成功提示收入笔数／合计，原文清空；协议、真实数据库集成、e2e 及合成真实模型样例。
- “工资到账 8000 元，午饭花了 35 元”及多笔混合收支 → 一个批次创建正确类型、分类和金额，总笔数及两类金额独立且准确；记录页与家庭汇总保持原类型行为；协议、数据库集成和中英文浏览器证据。
- 收到退款或报销 → 新增收入，既有支出及文件导入退款抵扣结果不被修改；来源三字段为空；数据库集成及文件导入回归。
- 明确另一位家庭成员获得收入、外部付款人出现、未明确获得者 → 分别归实际收入成员或当前登录成员，外部资金提供人不当家庭成员，创建人始终提交者；协议提示／真实模型合成样例及数据库证据。
- 相同名称的收入／支出分类、模型选择跨类型分类、候选中途停用／改名／改类型、未知成员／分类 → 合法候选按类型选择，失效或不匹配结果整段不入账；协议与数据库集成。
- 任一交易缺少金额、类型含糊、日期／成员不清、外币、纯转账、修改／删除请求、超限或异常输出 → 全批拒绝，原文保留，有效问题偏移能定位；不因“转账到账”四字误拒绝明确收入；unit、integration、e2e 与真实合成样例。
- 混合批次任一记录写入失败、会话中途过期／撤销、伪造身份或跨家庭查询 → 无部分交易、无成功快照或越权结果；真实数据库原子回滚和会话／身份集成证据。
- 纯收入、纯支出、混合成功及响应丢失后查询 → 总笔数与两类笔数／金额一致，同次请求至多创建一批，不再次产生创建活动；全批提交与错误纠错重放仍有效；并发集成与弱网 e2e。
- 旧纯支出成功快照、旧失败／关闭标记及问题偏移 → 新版仍可查询，金额及笔数不漂移；旧记录已编辑、删除或改类型后重放仍是原结果；不重开旧收入／退款拒绝终态，新 UUID 可使用新能力；旧结构／编辑删除／终态集成及浏览器恢复证据。
- 未受理查询关闭与首次受理竞争、过期恢复和旧尝试迟到 → 原锁及终态边界继续有效，收入及混合不能引入第二次写账；保留原竞争、过期和断网恢复回归。
- 协议版本不一致、缺失显式类型或无效新／旧快照 → 拒绝不可信模型结果，不猜测类型，不把无效持久结果宣告成功；旧页面无法正确展示新摘要时不误报支出合计或未入账，刷新使用原 UUID 确认；新旧请求／快照单元、集成及浏览器恢复证据。
- 出站请求、活动、诊断、日志、URL 和浏览器存储 → 模型只收到获准本次输入及必要类型候选；活动仅类型和笔数，客户端仅待确认 UUID，无原文、模型明细或凭据新增暴露；隐私集成、浏览器存储检查和安全审查。
- 最终实现 → lint、unit、integration、e2e、构建与合成真实 ACP 收入／退款／混合／原支出和分类建议 smoke 通过；安全审查记录 Findings、Verification、Residual Risk。按已确认 Git 偏好与实现同一 feature 提交，推送 master 核对 SHA 后从该提交部署、验证镜像／健康／内部模型端点，已有生产库不执行 seed。
