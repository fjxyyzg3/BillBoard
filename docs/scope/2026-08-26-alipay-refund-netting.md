# 支付宝退款净额导入

## 目标

支付宝官方 CSV 会把付款和后续退款分别列为支出与“不计收支”流水，现有导入器会导入原支出并把退款行判为不可导入，导致账本支出未扣除退款。本次改动在导入同一份 CSV 时识别并合并可可靠配对的付款与成功退款：完全退款不进入账本，部分退款只以差额形成最终支出。

## 决策基线

### 需求边界

- 只处理同一份支付宝 CSV 内同时存在的付款和退款，不搜索或修改历史交易。
- 退款必须同时满足 `收/支=不计收支`、`交易分类=退款`、`交易状态=退款成功`，并通过非空且完全相同的 `商家订单号` 与原付款配对；不使用交易对方、商品、时间或金额做启发式匹配。
- 同一订单的多笔成功退款累计计算。退款合计小于付款金额时，只生成一条差额支出；等于付款金额时，原付款显示为“已完全退款，自动跳过”且不能恢复导入；大于付款金额时整组不可导入。
- 差额支出沿用原付款的日期、交易分类、交易对方、成员归属和创建人归属；退款原始行不单独生成收入或支出。
- 孤立退款或缺少 `商家订单号` 的退款行本身不可导入，不影响无法证明相关的普通付款；同一非空订单号对应多笔原付款、组内付款或成功退款金额/日期无效以及其它无法唯一配对的情况，整组不可导入。两类失败都显示可理解的原因。
- 若原付款的来源指纹已存在于当前家庭的历史交易中，本次退款组不新增交易：部分退款的历史金额等于当前净额时按普通同源重复处理；历史金额与当前净额不同时提示用户人工调整既有交易；完全退款只要存在历史交易就提示人工调整。以上判断包含软删除交易，且不自动修改历史数据。
- 普通支付宝收入、支出及现有异常状态规则保持不变；微信支付、随手记和招商银行导入不受影响。
- 所有新增界面文案提供中文和英文版本。测试只使用合成的订单号、账户和商户信息，不把附件或其中的真实明细加入仓库。

### 技术决策

- 退款配对和金额归并属于支付宝来源解析职责，在 `parseAlipayCsv` 生成通用 `ParsedImportRow` 之前完成；草稿层不重新解析支付宝原始字段。
- 解析器先读取全部原始明细，只为至少包含一条严格成功退款候选的非空 `商家订单号` 建立退款分组，配对不依赖 CSV 行顺序。没有严格成功退款候选的订单完全沿用现有逐行解析，即使多笔普通付款共享同一 `商家订单号` 也不得触发歧义规则。
- 合法退款组折叠为以原付款为身份的一条解析结果。部分退款结果的 `amountFen` 为原付款金额分减累计退款金额分，时间、分类映射键及成员原始信息来自原付款。
- 折叠结果复用原付款按现有算法生成的 `sourceFingerprint`。草稿层按家庭和来源批量查询该指纹对应的历史 `amountFen`，查询不排除软删除记录：没有历史记录时首次净额可正常落库；历史金额等于当前净额时为普通同源重复；历史金额不等于当前净额时为退款变化冲突并提示人工调整；完全退款存在任意历史金额时同样提示人工调整。
- 解析结果携带草稿展示所需的退款处置原因，但不把 `商家订单号`、支付账号或退款原始详情写入 `Transaction.note`，也不新增 Prisma 字段或迁移。
- 不新增数据库枚举或字段。完全退款且不存在历史交易时持久化为 `status=USER_SKIPPED`、`userDecision=SKIP`、`skipReason=ALIPAY_FULLY_REFUNDED`；该稳定原因代码使页面显示只读的“已完全退款，自动跳过”，并使所有服务端行决策入口拒绝将其改为 `KEEP`。普通同源重复继续使用现有 `SOURCE_DUPLICATE` 语义；历史金额不同或完全退款已存在历史交易时持久化为 `status=SOURCE_DUPLICATE`、`userDecision=SKIP`、`skipReason=ALIPAY_REFUND_REQUIRES_MANUAL_ADJUSTMENT`，页面显示不可操作的人工调整提示。其它来源的 `USER_SKIPPED` 行仍保持现有可恢复行为。
- 汇总计数沿用现有类别：没有历史交易的完全退款计入 `total` 和 `userSkipped`，不计入 `importable` 或 `invalid`；普通重复及需人工调整的历史冲突计入 `total` 和 `sourceDuplicate`。确认导入始终忽略这两类锁定行。
- 金额继续只使用整数分；日期继续按原付款的 `Asia/Shanghai` 语义解析；同源重复查询继续包含软删除记录，家庭访问继续由 session 派生的 `householdId` 和 `memberId` 限制。

## 设计视图

### 功能设计

用户仍从 `/records/import` 选择支付宝并上传官方 CSV。上传后，普通交易按现有方式进入草稿；具备严格退款特征的行不再单独作为收入、支出或普通无效行处理，而是先与相同 `商家订单号` 的原支出归并。

部分退款在预览中表现为一条普通支付宝支出，金额已经扣除全部成功退款，并继续参与现有成员选择、分类映射、疑似重复检查和确认导入。完全退款在预览中保留原付款的日期、分类和原金额用于核对，同时显示“已完全退款，自动跳过”，用户不能将其改回保留。退款组无法可靠配对或金额异常时不允许导入，并显示对应原因。

当折叠后的原付款指纹已经存在时，预览不创建第二笔净额支出。历史金额与当前部分退款净额相同时只显示普通同源重复；金额不同时显示不可操作的人工调整提示；完全退款存在历史交易时也显示该提示。本期不提供自动修改、抵扣或软删除历史交易的能力。

### 技术设计

#### 整体方案

`src/lib/imports/sources/alipay.ts` 保留 CSV 解码、表头定位和单元格标准化职责，并增加原始行分类与退款归并步骤。归并器只消费当前文件中的标准化原始行，输出普通付款、净额付款、完全退款付款或不可导入行；随后复用既有金额、日期、分类和指纹转换逻辑生成 `ParsedImportWorkbook`。

`src/lib/imports/types.ts` 仅为解析结果补充非持久化的退款处置类型。`src/lib/imports/drafts.ts` 使用该类型和批量返回的历史指纹金额，写入上述稳定 `skipReason` 代码，并在唯一的 `setImportDraftRowDecision` 服务中执行锁定校验；批量表单提交也必须逐行经过该服务。导入页面从持久化的状态和原因代码恢复展示，`src/lib/i18n.ts` 提供中英文标签；不增加新的导入入口、Prisma 状态或数据库模型。

#### 关键结构

只有至少包含一条严格成功退款候选的非空 `商家订单号` 才进入下列分组；没有成功退款的订单全部继续走现有单行解析。每个退款分组包含零到多条付款候选和一到多条严格成功退款候选：

- 恰好一条有效支出付款且至少一条成功退款：累计退款并计算净额。
- 退款没有对应付款或缺少订单号：退款行不可导入，无法证明相关的普通付款继续按现有规则处理。
- 同一非空订单号存在多笔付款，或组内付款/成功退款数据无效：该订单号下的付款和退款全部不可导入。
- 净额大于零：输出一条净额付款。
- 净额等于零：输出一条完全退款的硬跳过付款。
- 净额小于零：输出不可导入组。

退款候选在参与上述分组后不再进入普通 `不计收支`/退款异常行处理；未配对退款仍沿用不可导入流转并获得更具体的原因。

#### 实现流程

1. 解码 CSV、定位表头并解析全部交易形态的原始行，同时保留原始行号和标准化 `商家订单号`。
2. 严格识别成功退款候选，只按这些候选的非空订单号建立分组并定位对应有效支出付款；其它订单不参与分组。
3. 对唯一配对组累计整数分退款金额，依据净额输出差额付款、完全退款硬跳过付款或不可导入组；未参与退款配对的行继续走现有单行解析规则。
4. 为可落库的差额付款生成原付款来源指纹，并保留退款处置类型供草稿层判定状态和提示。
5. 草稿创建按家庭和来源批量查询历史指纹及金额。部分退款没有历史记录时按现有分类映射与疑似重复流程处理；历史金额相等时标为普通同源重复，金额不同时写入人工调整原因；完全退款根据是否存在历史记录分别写入完全退款原因或人工调整原因。
6. 页面用持久化状态和原因代码显示只读退款处置行；`setImportDraftRowDecision` 拒绝把 `ALIPAY_FULLY_REFUNDED` 行改为保留，批量表单不得绕过该服务。
7. 确认导入沿用现有批量事务，只写入仍可导入的净额付款，不写入退款行、完全退款付款或历史冲突行。

## 验收

- 同一 CSV 中一笔 ¥1.80 支出与一笔 ¥1.15 成功退款具有相同非空 `商家订单号` → 预览和最终账本只出现一笔 ¥0.65 支出，日期、分类、交易对方和成员归属来自原付款；单元测试、集成测试和 E2E 断言。
- 同一订单存在多笔成功退款且累计金额小于付款 → 只导入付款减退款合计后的单笔支出；单元测试与集成测试断言金额分值及交易数量。
- 累计退款等于付款且历史中没有原付款 → 草稿行持久化为 `USER_SKIPPED/SKIP/ALIPAY_FULLY_REFUNDED`，预览显示一条“已完全退款，自动跳过”的付款并计入跳过数；页面不提供保留操作，直接调用 `setImportDraftRowDecision(..., KEEP, ...)` 或提交含 `KEEP` 的批量表单均被拒绝，确认后不创建交易；组件/集成测试与 E2E 断言。
- 累计退款大于付款，或付款无法唯一确定 → 整组不可导入且显示明确原因，确认其它有效行不受阻；单元测试与集成测试断言。
- 退款缺少订单号、订单号无对应付款，或不同时满足三个严格退款字段 → 不冲减任何付款；该退款不可导入，普通付款保持原金额；单元测试断言。
- 退款状态为处理中、失败或其它含“退款”但不等于 `退款成功` 的状态 → 不参与净额计算；单元测试断言。
- 同一订单号存在多笔普通付款但没有严格成功退款 → 所有付款继续按现有规则解析，不触发退款歧义或整组失效；现有及新增单元回归测试断言。
- 原付款总额已经存在于同一家庭历史交易，当前 CSV 首次带来部分退款净额 → 草稿持久化为 `SOURCE_DUPLICATE/SKIP/ALIPAY_REFUND_REQUIRES_MANUAL_ADJUSTMENT`，显示人工调整提示且不新增交易；集成测试覆盖有效及软删除历史交易。
- 已正确导入的历史金额等于当前部分退款净额，再次导入相同退款账单 → 标为普通同源重复，不显示人工调整提示且不重复创建交易；集成测试断言。
- 相同原付款后来出现更多退款，导致当前净额与历史金额不同 → 标为需人工调整的历史冲突，不新增交易；集成测试断言。
- 完全退款对应的原付款已经存在于历史交易 → 标为需人工调整的历史冲突，不新增交易；集成测试断言。
- 支付宝普通收入、普通支出、现有异常状态，以及微信支付、随手记、招商银行导入保持现有结果；现有单元、集成和 E2E 回归测试通过。
- 新增用户可见文案在中英文 locale 下均有对应值；i18n 单元测试断言。
- 实现不新增 Prisma 模型、字段或迁移，不把真实附件、账号、订单号、商户明细、凭据或生产入口写入 Git；schema diff 与针对性敏感文本检查验证。
- 完整实现通过 `npm run lint`、`npm run test:unit`、`npm run test:integration`、`npm run test:e2e`，并按 `skills/billboard-security-review/SKILL.md` 完成 Findings、Verification、Residual Risk 审查后才允许提交。
