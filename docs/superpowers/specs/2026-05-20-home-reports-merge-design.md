# 首页与报表合并设计

日期：2026-05-20

## 1. 背景与目标

当前 `Home` 和 `Reports` 的信息有明显重叠：

- `Home` 已经展示收入、支出、结余、记录数、趋势、支出分类和近期记录，并支持成员视角和快捷时间范围。
- `Reports` 主要补充月、年、全部范围，以及收入和支出分类占比，但 summary 和支出分类与首页重复。

本次设计目标是把报表能力合并进首页，删除独立报表入口，让应用继续服务三个核心场景：

- 快速记录。
- 按家庭成员视角查看。
- 按时间范围复盘。

本设计只定义信息架构、URL 规则、数据边界和验证计划，不直接实现代码。

## 2. 假设

- 合并后的唯一总览入口是 `/home`。
- 用户接受删除 `/reports` 路由，不保留跳转兼容。
- 首页和记录页必须共用同一套范围模型，避免 drill-down 后口径不一致。
- 新增记录仍默认当前时间，不根据历史月报或年报范围自动改写发生时间。
- 本次不新增预算、账户、分类管理、设置页或其他非核心功能。

## 3. 已比较方案

### 3.1 轻合并

把 `/reports` 的模块搬进首页，但保留首页快捷范围和报表月、年、全部两套筛选。

优点：

- 改动较少。
- 对现有记录页影响小。

缺点：

- 页面内仍有两套范围口径。
- 重复和解释成本没有真正消失。
- 用户已经明确不选择两套筛选。

### 3.2 统一筛选合并

`/home` 成为唯一总览页，首页和记录页都使用月、年、全部范围；导航只保留首页、记一笔、记录；首页保留总额卡片、趋势图和分类排行。

优点：

- 信息入口清晰。
- 首页和记录页查询口径一致。
- 分类、summary 和趋势都能自然钻取到记录页。
- 符合两人家庭记账的产品边界。

缺点：

- 记录页时间筛选需要同步迁移。
- 现有快捷范围测试和 e2e 需要更新。

结论：选择此方案。

### 3.3 纯报表化首页

首页变成纯复盘页面，弱化记录钻取和快速查看。

优点：

- 页面最短。
- 实现边界更接近传统财务报表。

缺点：

- 不利于从异常分类或趋势点直接定位明细。
- 偏离快速记录和低查看成本目标。

## 4. 信息架构

主导航只保留三项：

- `/home` 首页。
- `/add` 记一笔。
- `/records` 记录。

删除导航中的报表项。删除 `/reports` 页面，不做兼容跳转；旧链接访问时由 Next.js 走 404。

首页模块顺序：

1. 顶部：标题、月/年/全部范围控件、记一笔按钮。
2. 视角：家庭、我、配偶。
3. 总额卡片：收入、支出、结余、记录数。
4. 趋势图：月视图按天聚合，年和全部按月聚合。
5. 分类分析：单个排行模块，默认支出，可切收入。

移除首页近期记录模块。查看和编辑明细统一进入记录页完成。

## 5. URL 与筛选规则

统一范围模型使用报表语义：

```text
mode=month&month=2026-05&year=2026
mode=year&month=2026-05&year=2026
mode=all&month=2026-05&year=2026
```

默认打开 `/home` 时，使用 `Asia/Shanghai` 当前月份。`month` 和 `year` 保留在 URL 里，使用户在月、年、全部之间切换时能记住之前选择。非法值或超出数据范围的值按现有报表逻辑 clamp 到可用范围。

成员视角沿用现有参数：

- 不传 `perspective` 表示家庭。
- `perspective=me`。
- `perspective=spouse`。

分类模块切换写入 URL：

- 不传 `categoryType` 时默认 `expense`。
- `categoryType=expense`。
- `categoryType=income`。

首页跳转记录页时保留当前范围和成员视角，并按入口增加筛选：

- 收入卡片加 `type=income`。
- 支出卡片加 `type=expense`。
- 结余和记录数卡片不加类型。
- 分类项加 `type=expense|income&category=<id>`。
- 趋势点加合法 ISO 格式 `from` 和 `to`，用于精确钻取那一天或那个月。

记录页也使用同一套 `mode/month/year/perspective`。当 URL 同时有合法 `from/to` 时，记录列表查询优先使用 `from/to`；否则使用 `mode/month/year` 计算范围。范围控件仍显示 `mode/month/year`，这样用户从趋势点返回更大范围时仍有明确上下文。

## 6. 数据与组件边界

实现时应收敛到一套报表数据模型，而不是保留首页和报表两套查询。

计划边界：

- 复用或改造现有 `ReportRangeControls`，作为首页和记录页的统一范围控件。
- 将月、年、全部范围计算、可选范围、clamp 逻辑作为统一报表范围基础。
- 统一首页查询返回 summary、trend、expense categories、income categories。
- 首页查询必须继续基于当前 session 的 `householdId` 和 `memberId`，成员视角从同家庭成员列表派生。
- 有效交易查询继续包含 `deletedAt: null`。
- 金额继续使用整数分 `amountFen`，只在展示边界格式化。
- 日期范围继续固定按 `Asia/Shanghai` 计算。
- 分类排行复用当前首页 `CategoryBreakdown` 的轻量条形列表风格，扩展为支出/收入切换。
- 记录页 `listRecords` 改为接收统一范围选择，同时保留合法 `from/to` 精确钻取。
- `/add` 只透传筛选上下文，新增表单的默认发生时间仍是当前上海时间。

不做的事：

- 不新增分类。
- 不改 Prisma schema。
- 不新增报表缓存、预聚合表或后台任务。
- 不新增设置页、更多页或导入快捷导航。
- 不保留隐藏的 `/reports` 主流程入口。

## 7. 文案与导航

新增或改动 UI 文案必须同步 `src/lib/i18n.ts` 的中文和英文文案。

导航文案从四项收敛到三项：

- 首页。
- 记一笔。
- 记录。

如果 `reports` 文案不再被使用，实现时优先删除独立报表页相关文案，避免继续暴露“报表页”心智。通用分类、范围和 summary 文案可以迁移到新的首页文案结构中。

## 8. 验证计划

实现阶段建议验证：

1. Unit：统一范围解析、边界 clamp、分类类型 URL 默认值、趋势粒度、分类聚合。
2. Integration：首页统一查询按 `householdId`、`memberId`、`perspective`、`mode/month/year/all` 过滤；记录页列表使用同一范围；有效记录仍排除软删除。
3. Component：范围控件月、年、全部渲染和 URL 更新；分类支出/收入切换写入 URL。
4. E2E：从首页选择成员和月份，点支出卡、分类项、趋势点进入记录页，验证 URL 和记录结果；导航只剩三项；`/reports` 不再可访问。

代码实现提交前必须按仓库规则运行完整验证：

```text
npm run lint
npm run test:unit
npm run test:integration
npm run test:e2e
```

## 9. 风险与应对

- 风险：删除 `/reports` 导致旧链接 404。
  应对：这是已确认取舍；测试应明确验证不再从导航暴露报表入口。
- 风险：记录页从快捷范围迁移到月、年、全部后，旧测试和用户习惯受影响。
  应对：同步更新记录页测试和 e2e，确保首页到记录页口径一致。
- 风险：`from/to` 和 `mode/month/year` 同时存在时产生解释歧义。
  应对：查询优先级固定为合法 `from/to` 优先，范围控件继续展示 `mode/month/year`。
- 风险：当前饼图组件不再用于主流程。
  应对：实现时删除未使用引用；是否删除组件文件由实际引用关系决定，不额外保留隐藏页面。
- 风险：统一查询触及家庭财务数据隔离。
  应对：查询必须从 server session 派生 `householdId` 和 `memberId`，并对所有交易查询加 `deletedAt: null`。

## 10. 设计结论

本次合并采用统一筛选合并方案。`/home` 成为唯一总览入口，承载月、年、全部复盘；`/records` 使用同一范围模型承接 drill-down；`/add` 保持快速记录。页面不再保留独立报表入口和近期记录模块，分类分析使用可切换的轻量排行列表，以降低重复信息和查看成本。
