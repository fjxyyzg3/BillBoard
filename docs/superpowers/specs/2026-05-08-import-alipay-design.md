# 支付宝导入功能设计

日期：2026-05-08

## 1. 背景和目标

BillBoard 已支持随手记 `.xlsx` 和微信支付 `.xlsx` 导入，并已有导入草稿、分类映射记忆、同源去重、疑似重复确认和批量确认写入流程。支付宝导入的目标是在不增加记账阻力的前提下，把支付宝官方导出的 CSV 账单流水导入同一套家庭账本。

本期只支持支付宝官方导出的 `.csv` 文件。导入入口继续放在 `/records/import`，用户上传前显式选择来源：`随手记`、`微信支付` 或 `支付宝`。

样例文件观察：

- 文件名：`支付宝交易明细(20260407-20260507).csv`
- 编码：`GB18030`/`GBK` 中文 CSV。
- 文件头包含 `姓名：老公`、支付宝账户、起止时间、导出交易类型和汇总。
- 明细表头不在第 1 行，需要在文本中查找。
- 明细列包含 `交易时间`、`交易分类`、`交易对方`、`对方账号`、`商品说明`、`收/支`、`金额`、`收/付款方式`、`交易状态`、`交易订单号`、`商家订单号`、`备注`。
- 样例共 85 条记录，其中 `支出` 85 条，包含 `交易成功`、`支付成功` 和 `交易关闭` 状态。

## 2. 已确认假设

- 支付宝一期只支持官方导出的 `.csv`。
- 支付宝 CSV 按 `GB18030` 优先解码。
- 支付宝导入复用现有 `ImportDraft`、`ImportDraftRow`、`ImportCategoryMapping` 和 `Transaction` 来源字段。
- 不新增 Prisma 模型，不新增 `ImportDraft` 字段。
- 支付宝来源标识使用 `alipay`。
- 支付宝分类映射按 `收/支 + 交易分类` 聚合，减少同类商户重复手动映射。
- 支付宝账单的成员归属由页面下拉框决定。
- 成员下拉框默认值从文件头 `姓名` 推断；无法推断时使用当前登录用户。
- 修改支付宝账单归属成员时，直接批量更新该草稿所有未完成、非 `INVALID`、非 `SOURCE_DUPLICATE` 的支付宝行 `actorMemberId` 和 `createdByMemberId`。
- 支付宝账单明细没有独立的“记账人”和“成员”，所以同一个成员同时作为 `actorMemberId` 和 `createdByMemberId`。
- `不计收支` 标记为不可导入，不阻塞其它行。
- 金额为 0 或小于 0 的行标记为不可导入，不阻塞其它行。
- 退款、关闭、失败等状态标记为不可导入，不阻塞其它行。
- 未命中退款、关闭、失败关键词的未知状态按正常收入或支出导入。
- 金额继续使用整数分 `amountFen`。
- 时间继续按 `Asia/Shanghai` 语义解析，落库保存 UTC `Date`。
- 有效记录查询继续排除软删除数据。
- 所有访问和写入继续基于当前 session 的 `householdId` 和 `memberId` 校验。

## 3. 方案选择

采用方案：复用现有导入草稿主流程，新增支付宝 CSV 来源解析器，并把上传页改成按来源校验文件类型。

选择理由：

- 现有草稿流程已经覆盖上传后预览、分类映射、疑似重复确认和批量确认。
- 分类映射、同源去重、疑似重复、权限校验和批量确认可以复用。
- 支付宝只需要新增来源适配器和少量来源分发逻辑。
- 上传前选择来源可以给出更明确的 `.csv` 或 `.xlsx` 文件类型提示。
- 不做支付平台导入抽象，避免把微信 `.xlsx` 和支付宝 `.csv` 的差异过早泛化。

不采用方案：

- 支付宝专用导入页面：会复制草稿、映射、去重和确认逻辑，维护成本高。
- 抽象“支付平台导入”共用层：结构看似统一，但当前两个支付平台文件格式差异较大，容易过度设计。

## 4. 来源和数据模型

### 4.1 `ImportSource`

将现有来源扩展为三个来源：

- `sui_shou_ji`
- `wechat_pay`
- `alipay`

现有来源分发只扩展到支持第三个来源，不新增插件式注册机制。

### 4.2 现有表复用

不新增数据库字段。支付宝导入继续使用：

- `ImportDraft.source = alipay`
- `ImportDraftRow.mappingKey`
- `ImportDraftRow.primaryCategory`
- `ImportDraftRow.secondaryCategory`
- `ImportDraftRow.actorMemberId`
- `ImportDraftRow.createdByMemberId`
- `Transaction.source = alipay`
- `Transaction.sourceFingerprint`
- `Transaction.sourceImportedAt`
- `ImportCategoryMapping.source = alipay`

支付宝的 `primaryCategory` 保存 `交易分类`，`secondaryCategory` 保存 `交易对方`。分类映射项只显示并保存 `收/支 + 交易分类`，交易对方仍保留在草稿行和备注中供追溯。

```text
支出 · 餐饮美食
```

## 5. 支付宝 CSV 解析规则

### 5.1 文件识别

解析器读取文本后查找包含以下必需列的表头行：

- `交易时间`
- `交易分类`
- `交易对方`
- `对方账号`
- `商品说明`
- `收/支`
- `金额`
- `收/付款方式`
- `交易状态`
- `交易订单号`
- `商家订单号`
- `备注`

如果无法找到这些表头，上传失败，不生成草稿，并显示支付宝格式识别错误。

### 5.2 文件头姓名

解析器读取形如 `姓名：老公` 的文件头信息，输出可选的 `ownerName`。草稿创建时用现有成员别名规则推断默认成员：

- `老公` 或 `老公` 默认选“老公”。
- `老婆` 或 `老婆` 默认选“老婆”。
- 无法推断时默认选当前登录用户。

该默认成员会写入支付宝草稿行的 `actorMemberId` 和 `createdByMemberId`。预览页允许用户修改。

### 5.3 字段转换

- `收/支=支出` 映射为 `EXPENSE`。
- `收/支=收入` 映射为 `INCOME`。
- `收/支=不计收支` 标记为 `INVALID`。
- 其它 `收/支` 值标记为 `INVALID`。
- `交易状态` 包含退款、关闭、失败等关键词时标记为 `INVALID`。
- 未命中这些异常关键词的状态按正常记录导入。
- `金额` 转为整数分，必须大于 0。
- `交易时间` 按 `UTC+08:00` 解析为 `occurredAt`。
- `交易分类` 去除首尾空白后参与分类映射 key。
- `交易对方` 去除首尾空白后保存在草稿行和备注中，但不参与支付宝分类映射 key。
- 空字段和 `/` 视为空值，避免写入无意义备注片段。

### 5.4 CSV 处理

支付宝官方 CSV 可能包含文件头说明、空行、说明文字和尾部空列。解析器应：

- 用 `GB18030` 解码上传内容。
- 在所有行中查找明细表头，不假设表头在固定行。
- 使用 CSV 解析规则处理逗号和引号，不用简单字符串切分处理明细字段。
- 跳过表头前的说明行和表头后的空行。
- 保留交易订单号和商家订单号中的原始文本，生成指纹前做首尾空白清理。
- 限制可解析数据行不超过 20000 行，超限时不生成草稿。

### 5.5 备注生成

导入后写入 `Transaction.note`，保留支付宝关键原始信息，不把完整原始行塞入备注。

推荐格式：

```text
支付宝：交易分类；交易对方：交易对方；商品：商品说明；收/付款方式：收/付款方式；状态：交易状态；交易订单号：交易订单号；商家订单号：商家订单号；备注：备注
```

空字段不写入对应片段。支付宝原始字段为 `/` 时视为空。

### 5.6 来源指纹

支付宝同源精确去重基于稳定原始字段生成：

- 来源
- `收/支`
- `交易时间`
- `金额`
- 文件头 `姓名`
- `交易分类`
- `交易对方`
- `对方账号`
- `商品说明`
- `收/付款方式`
- `交易状态`
- `交易订单号`
- `商家订单号`
- `备注`

同一家庭下已存在同 `source + sourceFingerprint` 的交易时，草稿行标记为 `SOURCE_DUPLICATE` 并自动跳过。该规则包含软删除交易，避免删除后重复导入。

## 6. 页面和交互

### 6.1 上传入口

`/records/import` 上传区新增来源选择：

- `随手记`
- `微信支付`
- `支付宝`

选择随手记或微信支付时仍使用 `.xlsx`。选择支付宝时使用 `.csv`。文件大小限制沿用现有 20MB。

错误提示按来源区分：

- 随手记：无法识别随手记导出格式。
- 微信支付：无法识别微信支付账单格式。
- 支付宝：无法识别支付宝账单格式。

文件类型错误也按来源提示：

- 随手记和微信支付仅支持 `.xlsx`。
- 支付宝仅支持 `.csv`。

### 6.2 支付账单成员选择

支付宝和微信支付草稿预览都显示“账单归属成员”下拉框：

- 支付宝默认选中文件头姓名推断出的成员。
- 微信支付继续默认选中文件头昵称推断出的成员。
- 无法推断时默认选当前登录用户。
- 用户可以在确认导入前修改。
- 保存后批量更新该草稿所有未完成、非 `INVALID`、非 `SOURCE_DUPLICATE` 的支付账单行 `actorMemberId` 和 `createdByMemberId`。
- 已完成草稿不能修改成员。
- 随手记导入不显示该下拉框，继续沿用现有成员映射规则。

页面从草稿行中读取当前成员值展示，不新增草稿级数据库字段。

### 6.3 分类映射

分类映射 UI 沿用现有结构。支付宝映射项按 `收/支 + 交易分类` 聚合。

映射保存后写入 `ImportCategoryMapping`，同一家庭、同一来源、同一收支类型、同一交易分类下次自动复用。支付宝映射记录的 `secondaryCategory` 保存为空字符串；微信支付和随手记的映射粒度不变。

### 6.4 重复处理

同源精确重复继续自动跳过。

跨来源或手动疑似重复继续使用现有规则：

- 同一家庭。
- 同一天。
- 同金额。
- 来源不同，或已有记录为手动记录。

疑似重复默认保留，用户可以改为跳过。

## 7. 服务端边界

建议模块边界：

- `src/lib/imports/types.ts`：扩展 `ImportSource`，增加支付宝来源常量。
- `src/lib/imports/sources/alipay.ts`：支付宝 CSV 来源解析器。
- `src/lib/imports/drafts.ts`：新增支付宝草稿创建函数；把微信成员批量更新函数通用化为支付账单成员更新函数。
- `src/app/(app)/records/import/actions.ts`：上传 action 按来源校验文件类型并分发解析；成员保存 action 支持微信和支付宝支付账单草稿。
- `src/app/(app)/records/import/page.tsx`：上传来源选择增加支付宝；支付账单成员下拉支持微信和支付宝；来源化文案。
- `src/lib/i18n.ts`：补齐中英文文案。

实现时保持外科手术式修改，只抽取支持 `wechat_pay` 和 `alipay` 共用成员选择所需的最小逻辑，不重构完整导入框架。

## 8. 错误处理

- 未登录：重定向登录页。
- 当前用户没有家庭成员身份：拒绝访问。
- 来源未选择：回到导入页并提示选择导入来源。
- 文件类型错误：按来源提示 `.xlsx` 或 `.csv` 要求。
- 文件超过 20MB 或可解析数据行超过 20000 行：显示文件过大错误。
- 支付宝表头不匹配：显示“无法识别支付宝账单格式”。
- CSV 解码或解析失败：显示支付宝格式识别错误或通用上传失败。
- 金额、时间、收支类型等单行错误：标记该行为不可导入。
- `不计收支`：标记该行为不可导入。
- 金额为 0：标记该行为不可导入。
- 退款、关闭、失败状态：标记该行为不可导入。
- 分类未映射：阻止确认导入，并提示需要补全映射。
- 草稿已完成：不重复提交，不允许修改成员。

## 10. 一期不做

- 不支持非官方支付宝 CSV。
- 不支持支付宝 `.xlsx` 或其它格式。
- 不支持自动检测来源并跳过来源选择。
- 不把支付方式、交易对方、对方账号、交易订单号建成独立业务字段。
- 不自动创建 BillBoard 分类。
- 不导入 `不计收支`。
- 不导入 0 元记录。
- 不做退款净额抵消。
- 不新增独立支付宝导入页面。
- 不新增复杂草稿管理列表。
- 不提供多来源插件注册系统。

## 12. 设计自检

- 本设计聚焦支付宝官方 `.csv` 导入，没有引入无关页面或分类管理能力。
- 支付宝复用现有导入草稿链路，避免复制确认、去重和权限逻辑。
- 支付宝成员下拉复用微信支付交互，不新增数据库字段。
- 分类映射粒度明确为 `收/支 + 交易分类`，交易对方不参与支付宝映射。
- `不计收支`、0 元和退款类状态不会污染收入支出账本。
- 同源去重和跨来源疑似重复继续沿用现有语义。
- i18n、测试和验证要求覆盖了新增用户可见行为。
